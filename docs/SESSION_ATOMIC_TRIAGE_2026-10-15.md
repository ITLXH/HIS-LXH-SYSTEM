# Atomic triage save — 2026-10-15
Before implementation: history insert and Visit update are separate; failure after history can leave partial progress and retry duplicates. Plan: authenticated RPC validates active staff/write actions for both tables, locks Visit, compares snapshot, inserts history and updates Visit in one transaction. Private per-user request receipt supports retry after a lost response; changed draft is blocked until old request reconciles. No unsafe fallback when RPC absent. No real patient writes or production SQL installation.
Affected: new migration, triageAtomicSave module, main triage submit and synthetic SQL/client tests. Risks: hosted schema/helpers/JWT still require staged UAT; legacy clients remain separate-write until safely refreshed. Preserve original migrations and all existing data. Never deploy before RPC/staging gates.

## Implementation and verification
RPC uses SECURITY DEFINER with empty search_path and explicit auth.uid + active profile + table write permission checks on EVERY call (including receipt replay). Receipt table has no authenticated/anon grants: clients cannot forge success receipts. Before installation, verify hosted helper definitions and any narrower patient/Visit access rules; explicit role checks must match actual clinic scope. Never install to an environment with unreviewed auth helpers. Service credentials are not used in the browser.
Visit is locked and compared with expected snapshot; history, Visit update and private receipt commit together. Optional legacy Visit BP/RR/O2 columns may be omitted, while full values remain in history. Other missing fields reject and roll back. Matching Visit/Patient required. Unknown fields rejected. Original migrations are untouched.
Client shares one pending save guard, preserves exact request on ambiguous transport failure, blocks changed draft until original request is reconciled, and replays confirmed request for duplicate same-form submit. Retry receipt is in memory only: reload/browser close loses the draft, so staff must inspect Visit/history before a new save after reload. This is NOT durable offline storage. Snapshot is acquired at submit; full form-open concurrency awareness remains future work.
